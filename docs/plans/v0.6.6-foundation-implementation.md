### Presentation and locale routes

All presentation responses use `Cache-Control: no-store` in v0.6.6. This is
deliberately conservative for a small local operator surface and prevents
cross-version stale assets without adding content hashing.

```text
GET /api/locale-bootstrap
GET /assets/public/public.css
GET /assets/public/setup.js
GET /assets/public/login.js
GET /assets/public/locales/{locale}.json

GET /assets/operator/operator.css
GET /assets/operator/shared.js
GET /assets/operator/dashboard.js
GET /assets/operator/settings.js
GET /assets/operator/locales/{locale}.json
```

The bootstrap body is ASCII-field-ordered:

```json
{"installed_locales":["en-US"],"server_default":"en-US"}
```

`en-XA` is available only to committed tests and is rejected by production
preference APIs. Public catalog ids are every `setup.*`, every `login.*`, and
the explicit `common.app_name` id; no other `common.*` id is implicitly public.

Server-default changes use `POST /api/settings/locale`. An authenticated user
changes or clears their own preference with the existing
`POST /api/settings/account` action `locale`. A syntactically valid but
uninstalled locale returns `locale_not_installed`.

### Canonical history wire

Canonical records are JSON objects serialized in the field order shown:

```json
{"format":"nimproxy-history","v":1,"kind":"boot","timestamp":1000,"boot_id":"boot-a","capacity":{"capacity_rpm":80,"enabled_keys":2,"key_rpms":[40,40]}}
{"format":"nimproxy-history","v":1,"kind":"sample","timestamp":1000,"boot_id":"boot-a","capacity":{"capacity_rpm":80,"enabled_keys":2,"key_rpms":[40,40]},"state":[{"kind":"counter","metric":"nimproxy_requests_total","labels":{"client":"client-a"},"value":1.0}]}
{"format":"nimproxy-history","v":1,"kind":"checkpoint","timestamp":1300,"boot_id":"boot-a","capacity":{"capacity_rpm":80,"enabled_keys":2,"key_rpms":[40,40]}}
```

- `history-v1.jsonl` is the only canonical path.
- The production canonical reader never reads `history.jsonl`, and runtime
  never renames, truncates, or deletes it. Task 10 may inspect it offline,
  read-only, solely to derive sanitized structural test evidence.
- File order is authoritative. Timestamps must be nondecreasing; equal values
  are allowed. A regression invalidates the current epoch.
- Unknown `format` or `v` anywhere refuses startup without modifying the file.
  An unknown v1 `kind` invalidates the current epoch until a valid boot and
  sample re-establish state.
- Unknown non-state object fields are ignored. Invalid state entries invalidate
  the complete sample.
- First creation uses a synced unique same-directory temporary file followed
  by atomic no-overwrite publication using `std::fs::hard_link`, removal of
  the temporary name, and directory sync. No dependency is added.
- The old-file warning is emitted once at startup and contains only the legacy
  path and byte length. Stale canonical temporary files are counted/reported
  once and never parsed or automatically deleted.

Query-scoped completeness is exposed as `window.complete: bool`.
`HistoryDiagnostics` contains these ASCII-ordered fields:

```rust
pub struct HistoryDiagnostics {
    pub excluded_epochs: usize,
    pub excluded_records: usize,
    pub normalized_series: usize,
    pub skipped_metric_lines: usize,
    pub valid_checkpoints: usize,
    pub valid_samples: usize,
}
```

### NIM observation contract

The private observation core uses:

```rust
enum Observation {
    Measured(u64),
    Estimated(u64),
    Unavailable,
    Invalid,
}

enum UsageField {
    PromptTokens,
    CompletionTokens,
    TotalTokens,
    CachedTokens,
    ReasoningTokens,
}
```

The field/outcome matrix is fixed:

| Field | Measured | Estimated | Unavailable | Invalid |
|---|---|---|---|---|
| `PromptTokens` | present valid integer | never | absent | wrong type/range |
| `CompletionTokens` | present valid integer | successful SSE with no measured completion: count parsed, nonterminal upstream `data:` events | absent from a buffered response or no countable SSE event | wrong type/range |
| `TotalTokens` | present valid integer consistent with checked prompt + completion when both are measured | never | absent | wrong type/range, checked-add overflow, or smaller than measured prompt + completion |
| `CachedTokens` | present valid integer not exceeding measured prompt | never | absent | wrong type/range, prompt not measured, or exceeds measured prompt |
| `ReasoningTokens` | present valid integer not exceeding measured completion | never | absent | wrong type/range, completion not measured, or exceeds measured completion |

One invalid relationship changes only the participating field/child outcomes;
it does not erase unrelated measured siblings. The only estimator is the
existing completed-stream event count for `CompletionTokens`. It remains in
`nimproxy_completion_tokens_total{source="estimate"}` and is displayed
separately from measured usage; buffered responses and incomplete streams are
never estimated. A valid numeric zero is `Measured(0)`.

Finish and tool-call observations are also fixed. A buffered response records
one bounded finish-reason result per choice and sums actual `message.tool_calls`
array lengths. A streamed response records one terminal finish reason per
choice index and counts unique `(choice_index, tool_call_index)` pairs across
deltas; repeated fragments do not add calls. Missing terminal reasons are
unavailable, conflicting/mistyped reasons for one choice are invalid, and
unknown strings map to the existing bounded `other` value. A valid choices
array with no tool calls is measured zero; malformed choices/tool-call arrays
or indexes are invalid, and absent choices are unavailable. Neither surface is
estimated, and no raw upstream value becomes a metric label.

Availability is exported only as:

```text
nimproxy_usage_observations_total{
  field="prompt_tokens|completion_tokens|total_tokens|cached_tokens|reasoning_tokens",
  result="measured|estimated|unavailable|invalid"
}
```

No new availability field is added to the dashboard API. The dashboard
consumes the bounded series already carried in its metrics payload. Standard
SSE `data:` lines are assembled into one observation event; upstream bytes
remain untouched. If an event cannot be safely observed, its fields are
unavailable or invalid rather than reconstructed by guesswork.
